# 競品價格監控與通知：設計文件

- 日期：2026-10-12
- 狀態：已確認設計，待撰寫實作計畫
- 品牌：逅斯蓋工作室（Code Sky）作品集，作品 1

## 1. 目的與情境

**客戶情境**：電商賣家需要監控競爭對手的商品價格與庫存。目前靠人工逐一查看，費時又容易漏掉變化。

**這個作品要證明的事**：能交付一套「定時爬取 → 偵測變化 → 即時通知」的自動化系統，而且網站改版時能主動發現問題。它對應服務方案「定時監控 + 通知」，以及後續的月費維運。

### 範圍

第一版包含：

- 3 家自架的模擬競品商城，價格與庫存會自動變化
- 定時爬取、變化偵測、Telegram 與 LINE 通知
- 簡單的儀表板：管理監控商品、查看價格走勢與事件紀錄
- 在本機用 Docker Compose 一鍵啟動

第一版不包含：

- AI 摘要（第二版再加；架構上只需新增一個讀取 Event 的元件）
- 登入與多使用者
- 線上部署（本機驗證完成後，再和其他作品統一部署到小型 VPS）
- 爬取真實電商網站

## 2. 架構

用 Docker Compose 跑兩個服務，共用同一個 Docker 映像，以不同的啟動指令區分：

```
┌──────────────┐  定時爬取 (HTTP)  ┌──────────────────┐
│ monitor      │ ────────────────▶ │ mock-shops       │
│ (port 8000)  │                   │ (port 8001)      │
│ 儀表板 + 排程 │                   │ 3 家模擬競品商城   │
└──────┬───────┘                   └──────────────────┘
       │ 通知
       ▼
 Telegram / LINE / 終端機
```

### 2.1 mock-shops（模擬商城）

- 3 家商城共用同一份商品資料，但 HTML 結構各不相同：
  - 商城 A：表格列表
  - 商城 B：卡片網格
  - 商城 C：只有商品詳細頁
- 背景排程每隔幾分鐘隨機調整價格與庫存。
- 提供管理端點，可以手動觸發變動，錄製 demo 時不必等排程。

### 2.2 monitor（監控主程式）

| 元件 | 職責 |
|---|---|
| `scrapers/` | 每家商城一個 adapter，統一介面為「輸入網址 → 回傳商品快照（名稱、價格、庫存）」；依網址的網域自動選用 adapter |
| `scheduler` | 用 APScheduler 定時對所有監控商品執行爬取，並將快照存入資料庫 |
| `detector` | 比較新快照與上一筆快照，產生事件 |
| `notifiers/` | 統一介面為「送出事件」；實作 Telegram、LINE、終端機三種；由設定決定啟用哪些，可以同時啟用多種 |
| `web` | FastAPI + Jinja2 + HTMX 的伺服器端渲染儀表板，走勢圖使用 Chart.js |

擴充方式：

- 新增一家要監控的網站：新增一個 adapter
- 新增一種通知管道：新增一個 notifier

### 2.3 資料模型

使用 SQLite，透過 SQLAlchemy 存取，之後可以直接換成 PostgreSQL。

| 資料表 | 欄位重點 |
|---|---|
| `Product` | 網址、商城、名稱、降價通知門檻（%）、最後檢查時間、狀態、連續失敗次數 |
| `Snapshot` | 所屬商品、價格、庫存、爬取時間 |
| `Event` | 所屬商品、事件類型、變化前後的值、建立時間 |
| `EventDelivery` | 所屬事件、通知管道、是否成功、最後嘗試時間 |

事件類型：`price_drop`、`price_rise`、`out_of_stock`、`restock`、`monitor_error`、`monitor_recovered`。

## 3. 資料流

每次排程執行（間隔可以設定，預設 10 分鐘；錄製 demo 時可以設為 1 分鐘）：

1. 取出所有監控商品。
2. 逐一處理每個商品：依網域選用 adapter → 抓取網頁 → 解析 → 存入 Snapshot。
3. detector 比較新舊快照，產生 Event。
4. 對每個尚未通知的 Event，用所有已啟用的管道送出；全部管道都成功後，標記為已通知。

### 事件規則

- 價格變動幅度大於或等於該商品的門檻（預設 5%）時，產生 `price_drop` 或 `price_rise`。
- 庫存從有貨變成缺貨時產生 `out_of_stock`；從缺貨變成有貨時產生 `restock`。不受門檻影響。
- 商品的第一筆快照只建立基準，不產生事件。

## 4. 錯誤處理

| 狀況 | 處理方式 |
|---|---|
| 網路錯誤、逾時 | 逾時 10 秒，最多重試 3 次，每次間隔遞增 |
| 解析失敗（找不到價格等欄位） | 歸類為「網站結構可能已改版」，與網路錯誤分開記錄 |
| 單一商品失敗 | 不影響其他商品，繼續處理下一個 |
| 連續失敗 3 次 | 產生 `monitor_error` 事件並通知，只通知一次；恢復正常時產生 `monitor_recovered` |
| 通知送出失敗 | 不影響其他管道；只要有任一管道失敗，事件就保持「未通知」，下次排程時只對失敗的管道重送 |

- 儀表板顯示每個商品最後檢查的時間與狀態，異常的商品標成紅色。
- 爬取禮節：同一網站的請求之間加入間隔，並使用可識別身分的 User-Agent。

「只對失敗的管道重送」由 `EventDelivery` 支援：每個事件在每個管道各有一筆送出紀錄，「已通知」等於所有已啟用管道的紀錄都成功，避免重送時讓已成功的管道收到重複通知。

## 5. 設定

透過環境變數設定，並提供 `.env.example`：

| 變數 | 說明 |
|---|---|
| `SCRAPE_INTERVAL_MINUTES` | 排程間隔，預設 10 |
| `TELEGRAM_BOT_TOKEN`、`TELEGRAM_CHAT_ID` | 有設定就啟用 Telegram |
| `LINE_CHANNEL_ACCESS_TOKEN`、`LINE_USER_ID` | 有設定就啟用 LINE（Messaging API 的 push message） |

Telegram 與 LINE 都沒有設定時，自動改用終端機輸出，讓任何人都可以直接用 `docker compose up` 看到完整流程。

## 6. 測試

使用 pytest；測試中不呼叫真實的 Telegram 或 LINE。

| 對象 | 做法 |
|---|---|
| adapters | 將三家商城的 HTML 存成測試檔，離線測試解析結果；另外準備「改版後」的 HTML，確認會拋出解析錯誤 |
| detector | 純邏輯測試：門檻邊界值、第一筆快照、缺貨與補貨的轉換 |
| notifiers | 用 respx 模擬 HTTP，檢查送出的內容格式；模擬送出失敗時，確認事件保持「未通知」 |
| 整合測試 | 在同一個程序內啟動 mock-shops，跑一輪完整排程，用假的 notifier 收集事件並驗證 |
| web | 冒煙測試：頁面能正常開啟，能新增與刪除監控商品 |

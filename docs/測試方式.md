# 測試方式

本地有三種測試方式，可以依需求選用：

| 方式 | 適合的時機 |
|---|---|
| 1. 自動化測試 | 改完程式碼後確認沒有改壞，速度最快 |
| 2. Docker Compose | 驗證完整系統，最接近正式環境 |
| 3. 直接執行兩個服務 | 開發時邊改邊看，支援自動重新載入 |

第一次使用前先安裝套件：

```bash
uv sync
```

## 1. 自動化測試

```bash
uv run pytest                                                          # 全部測試
uv run pytest tests/test_integration.py -v                             # 只跑某個檔案
uv run pytest tests/test_detector.py::test_price_threshold_boundary    # 只跑單一測試
uv run ruff check . && uv run ruff format --check .                    # lint 與格式檢查
```

- 測試不會連網路，也不會真的送出 Telegram 或 LINE 通知；HTTP 一律用 respx 模擬。
- 整合測試會在同一個程序內啟動模擬商城，跑完整排程。

| 測試檔 | 內容 |
|---|---|
| `test_detector.py` | 門檻邊界值、第一筆快照、缺貨與補貨的轉換 |
| `test_pchome.py` | 用 `tests/fixtures/pchome_*.json` 離線測試 PChome adapter：有貨、缺貨、API 格式改變時拋出解析錯誤 |
| `test_scrapers.py` | 用 `tests/fixtures/` 的 HTML 離線測試三個 adapter；用改版後的 HTML 確認會拋出解析錯誤；確認重試次數 |
| `test_notifiers.py` | Telegram 與 LINE 的送出格式；送出失敗時，事件保持「未通知」，而且只對失敗的管道重送 |
| `test_integration.py` | 完整排程：降價與缺貨事件、網站改版時只通知一次並在恢復時通知、網路錯誤分開記錄 |
| `test_web.py` | 儀表板冒煙測試：頁面能開啟、能新增與刪除監控商品、預設監控商品的建立 |

## 2. 用 Docker Compose 執行完整系統

```bash
cp .env.example .env
# 編輯 .env，把 SCRAPE_INTERVAL_MINUTES 改成 1，不必等太久
docker compose up --build
```

- 儀表板：<http://localhost:8000>
- 模擬商城：<http://localhost:8001>，頁面上有按鈕可以觸發「隨機變動」和「模擬改版」
- 沒有設定 Telegram 或 LINE 時，通知會輸出在終端機：`docker compose logs -f monitor`
- 啟動後會自動建立 6 個預設的監控商品（由 `docker-compose.yml` 的 `SEED_URLS` 設定）。
- 清除所有資料重新開始：`docker compose down -v`

## 3. 不用 Docker，直接執行兩個服務

開兩個終端機：

```bash
# 終端機 1：模擬商城
uv run uvicorn mock_shops.app:app --port 8001 --reload

# 終端機 2：監控主程式（每 1 分鐘檢查一次，並預先建立兩個監控商品）
SCRAPE_INTERVAL_MINUTES=1 \
SEED_URLS="http://shop-a.localhost:8001/products#P001,http://shop-c.localhost:8001/item/P002" \
uv run uvicorn --factory monitor.web.app:create_app --port 8000 --reload
```

- 資料庫預設存在 `data/monitor.db`；想重新開始，就刪除這個檔案。
- `SEED_URLS` 只在資料庫沒有任何商品時才生效。

## 手動觸發變化並觀察通知

方式 2 或方式 3 的服務啟動之後，可以用以下指令製造變化，不必等模擬商城的自動變動：

```bash
# 降價約 20%：下一輪排程會送出降價通知
curl -X POST localhost:8001/admin/items/shop-a/P001 \
  -H 'content-type: application/json' -d '{"price": 1590}'

# 缺貨：下一輪排程會送出缺貨通知
curl -X POST localhost:8001/admin/items/shop-c/P002 \
  -H 'content-type: application/json' -d '{"stock": 0}'

# 隨機變動每家商城的 1 到 2 個商品
curl -X POST localhost:8001/admin/mutate

# 模擬網站改版：連續 3 輪失敗後送出一次「監控異常」，儀表板中該商品標成紅色
curl -X POST "localhost:8001/admin/redesign/shop-c?enabled=true"

# 還原改版：下一輪排程會送出「監控恢復」
curl -X POST "localhost:8001/admin/redesign/shop-c?enabled=false"

# 把所有商城的價格、庫存與改版狀態還原成初始值
curl -X POST localhost:8001/admin/reset
```

## 監控真實的 PChome 商品

方式 2 或方式 3 的服務啟動之後，在儀表板貼上 PChome 24h 的商品頁網址，例如 `https://24h.pchome.com.tw/prod/DYAJCH-1900JLHPE`。

- 每檢查一個商品，會對 PChome 發出 2 次請求（價格 API 與搜尋 API）。請保持預設的 10 分鐘間隔，不要用 1 分鐘的 demo 間隔長時間監控真實網站。
- 真實商品的價格不會隨意變動，所以 demo 通知時仍然使用模擬商城。

單獨確認 adapter 能不能抓到資料：

```bash
uv run python -c "
import asyncio
from monitor.scrapers import get_adapter
from monitor.scrapers.fetch import Fetcher, make_client
async def main():
    url = 'https://24h.pchome.com.tw/prod/DYAJCH-1900JLHPE'
    async with make_client() as c:
        print(await get_adapter(url).scrape(url, Fetcher(c)))
asyncio.run(main())"
```

## 測試真實的 Telegram 或 LINE 通知

在 `.env`（方式 2）或環境變數（方式 3）填入：

- Telegram：`TELEGRAM_BOT_TOKEN`、`TELEGRAM_CHAT_ID`
- LINE：`LINE_CHANNEL_ACCESS_TOKEN`、`LINE_USER_ID`

啟動時，log 中的「啟用的通知管道」會列出 `telegram` 或 `line`。兩者都設定時會同時送出。

## 注意事項

- `shop-a.localhost` 這類網址在本機瀏覽器請用 Chrome 或 Firefox 開啟，Safari 可能無法解析。
- 修改模擬商城的模板或 `mock_shops/catalog.py` 的價格後，要重新產生 `tests/fixtures/` 中的 HTML，並更新 `tests/test_scrapers.py` 的預期值。
